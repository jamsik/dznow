# Развернуть DZNOW на сервере

Цель: открыть приложение из Telegram по кнопке бота и дать потыкать
нескольким людям. Продакшеном это ещё не будет — в конце написано, чего
для него не хватает.

## Что получится

```
Telegram ──кнопка бота──► https://ваш-адрес ──► контейнер dznow-app
                                                 ├── приложение (собранный фронт)
                                                 ├── /api — проекты, рендер
                                                 └── Chromium, снимает PNG 1080×1920
                          контейнер dznow-bot ──► показывает кнопку, больше ничего
```

Два контейнера в своём compose-проекте `dznow`. Соседний бот, который у вас
уже работает, они не трогают: другие имена, другие тома, другой образ.
Наружу торчит только адрес, который вы выберете на шаге 3.

**Где авторизация.** Отдельной регистрации нет и не будет. Telegram, открывая
Mini App, передаёт в неё подписанную строку `initData`; API проверяет подпись
HMAC по токену бота (`api/app/auth.py`) и достаёт оттуда, кто пришёл. Поэтому
токен бота — это и есть ключ авторизации, и поэтому анонимный вход
выключается сам, как только `BOT_TOKEN` появился в окружении.

## Шаг 1. Бот

В Telegram напишите [@BotFather](https://t.me/BotFather):

```
/newbot
```

Он спросит имя (любое, например `DZNOW`) и username — он должен заканчиваться
на `bot`, например `dznow_test_bot`. В ответ придёт токен вида
`8123456789:AAH...` — это пароль от бота, его нельзя публиковать и нельзя
коммитить.

Больше в BotFather ничего настраивать не нужно: кнопку меню бот пропишет себе
сам при первом запуске.

## Шаг 2. Положить код на GitHub

На вашем компьютере, в обычной командной строке. Если git не стоит:

```bat
winget install Git.Git
```

После установки закройте и откройте окно командной строки заново — иначе
`git` не найдётся в PATH.

```bat
cd F:\DZNOW
git init -b main
git add .
git commit -m "DZNOW: Mini App, рендер PNG, деплой в Docker"
```

Теперь заведите пустой репозиторий на <https://github.com/new>: имя `dznow`,
публичный, **без** галочек «Add a README», «Add .gitignore», «Choose a license» —
иначе первый `push` упрётся в конфликт. И свяжите:

```bat
git remote add origin https://github.com/ВАШ_ЛОГИН/dznow.git
git push -u origin main
```

При первом `push` откроется окно входа в GitHub — войдите браузером.

Токен бота в репозиторий не попадёт: он живёт в `.env`, а `.env` перечислен
в `.gitignore`. Проверить, что ничего лишнего не уехало, можно так:

```bat
git ls-files | findstr /i ".env"
```

Должно найтись только `.env.example` — файл с пустыми значениями.

## Шаг 3. Поднять на сервере

Сервер уже разведан: Ubuntu, Docker, nginx **на хосте** (не в контейнере) держит
80 и 443, соседний проект `friends-gacha` опубликован на `127.0.0.1:8000` и
описан в `/etc/nginx/sites-enabled/friends-gacha`. Порт 8010 свободен.

Значит, схема ровно та же, что у соседа: контейнер слушает локальный порт,
наружу выпускает nginx. Ничего нового открывать не нужно, и `friends-gacha`
не затрагивается — у DZNOW свой файл сайта, свой compose-проект, свои тома.

```
              ┌── nginx (хост, :80 :443) ──┐
интернет ─────┤                            ├── 127.0.0.1:8000 → friends-gacha
              └────────────────────────────┴── 127.0.0.1:8010 → dznow (новый)
```

### 3.1. Поддомен

Домен уже есть — `varezhka.top`, сертификаты выпускает certbot. Берём
поддомен **`dznow.varezhka.top`**.

Единственное, что делается руками и не автоматизируется: в панели регистратора
(там же, где заведён `varezhka.top`) добавить A-запись

```
dznow   A   <IP этого сервера>
```

IP сервера: `curl -s ifconfig.me`. Что запись разошлась, проверяется так —
обе команды должны вернуть один и тот же адрес:

```bash
curl -s ifconfig.me; echo
dig +short dznow.varezhka.top
```

Обычно это минуты, иногда до часа. Пока `dig` молчит, certbot запускать
бессмысленно: Let's Encrypt не сможет подтвердить домен.

Существующий сертификат тут не поможет: он выписан на `varezhka.top` и
`www.varezhka.top`, поддомены в него не входят. Certbot выпишет отдельный,
конфиг `friends-gacha` при этом не изменится.

### 3.2. Контейнеры

```bash
cd /opt
git clone https://github.com/ВАШ_ЛОГИН/dznow.git   # рядом с /opt/friends-gacha
cd dznow
cp .env.example .env
nano .env
```

В `.env` заполнить три строки (`APP_DOMAIN` нужен только профилю caddy, его
здесь не используем — оставьте пустым):

```
BOT_TOKEN=8123456789:AAH...
APP_URL=https://dznow.varezhka.top
BOT_USERNAME=dznow_test_bot
```

```bash
docker compose up -d --build
docker compose ps          # app healthy, bot running
curl -s localhost:8010/api/health    # {"ok":true}
```

Первая сборка небыстрая: внутрь образа ставится Chromium.

### 3.3. nginx

В репозитории лежит готовый файл, поддомен в нём уже проставлен:

```bash
sudo cp deploy/nginx/dznow.conf /etc/nginx/sites-available/dznow
sudo ln -s /etc/nginx/sites-available/dznow /etc/nginx/sites-enabled/dznow
sudo nginx -t && sudo systemctl reload nginx
```

`nginx -t` обязателен: с ошибкой в конфиге nginx не перезапустится и уронит
заодно соседний сайт. Пока `-t` не сказал `syntax is ok`, `reload` не делать.

Сертификат:

```bash
sudo certbot --nginx -d dznow.varezhka.top
```

Certbot сам допишет в файл блок `:443` и редирект с `:80` — ровно так же, как
он это сделал для `friends-gacha` (там его следы видны по комментариям
`# managed by Certbot`). Certbot на сервере уже стоит и работает.

### 3.4. Запустить бота

Бот стартует вместе со всеми, но `APP_URL` он читает при старте — если вписали
его после первого `up`, перезапустите:

```bash
docker compose up -d bot
docker compose logs bot   # «бот @… запущен, приложение: https://…»
```

### Если поддомена не будет

В `docker-compose.yml` остались два профиля на этот случай — Caddy со своим
доменом и Cloudflare-туннель без домена вообще. Для вашего сервера они не
нужны: Caddy подрался бы с nginx за порты 80 и 443.

## Память: обязательный swap

Сервер уже один раз завис из-за этого, поэтому пункт не «желательно», а
«сделать до следующего запуска».

Машина — 957 МБ без файла подкачки. Chromium на странице 1080×1920 просит
300–400 МБ, рядом живут два контейнера гачи, nginx и сам Docker. Когда
память кончается, ядро начинает убивать процессы по своему усмотрению —
и убивает не обязательно виновника: в прошлый раз досталось боту DZNOW,
потом завис health-check, а потом перестал отвечать SSH.

**Swap на 2 ГБ.** Пять команд, машину перезагружать не нужно:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h                      # в строке Swap должно появиться 2,0Gi
```

Последняя строка добавляет swap в `/etc/fstab`, иначе он пропадёт после
перезагрузки.

Swap — это не «больше памяти», а страховка: система начинает тормозить
вместо того, чтобы убивать процессы. Для сборки картинок раз в минуту
этого достаточно.

**Что уже сделано в коде.** У контейнера `app` стоит `mem_limit: 600m`:
теперь при нехватке памяти упирается и падает только он, а сервер остаётся
на связи. Chromium запускается с урезанным набором подсистем, контекст
пересоздаётся каждые 20 макетов, а после 10 минут простоя браузер
закрывается целиком — ночью DZNOW не занимает ничего. Очередь ограничена
тремя заданиями: четвёртый получит честное «попробуйте через минуту»
вместо общего зависания.

**Заодно приберитесь.** Старые образы после пересборок занимают гигабайты:

```bash
docker image prune -a -f
docker builder prune -f
df -h /
```

**Что дальше.** Всё перечисленное — обход тесноты, а не решение. Два
гигабайта памяти у VPS стоят недорого и снимают вопрос: тогда в
`docker-compose.yml` можно поднять `mem_limit` до `1g`, и рендер перестанет
ходить по краю.

## Диск: что его съедает

18 сентября диск заполнился на 100 %, и сервер начал отвечать «500 Internal
Server Error» — страницей nginx, не приложения. В `/var/log/nginx/error.log`
это видно прямым текстом:

```
pwritev() "/var/lib/nginx/proxy/…" failed (28: No space left on device)
```

nginx не смог записать временный файл и оборвал запрос. Приложение при этом
было живо и ни при чём.

**Что намерили.** Здесь важен порядок: сначала измерить, потом чистить.
Первые две догадки — «старые образы Docker» и «логи контейнеров» — обе
оказались мимо, и `du` это показал за минуту:

```
journalctl --vacuum   →  освобождено 1,7 ГБ   ← единственная подтверждённая находка
docker image prune    →  1,3 МБ
docker builder prune  →  47 МБ
/var/lib/docker целиком  37 МБ
логи контейнеров         14 МБ
```

То есть Docker к переполнению почти не причастен. Полтора гигабайта съел
журнал systemd: у него по умолчанию нет разумного потолка, он берёт до
10 % раздела.

Остальное распределено так (17 ГБ занятого):

```
/opt   5,8 ГБ      /var   5,4 ГБ      /usr   3,6 ГБ
```

Если `/var/lib/docker` занимает 37 МБ, а образ `dznow-app` с Chromium весит
около двух гигабайт — значит, Docker хранит данные не там. Проверяется
`docker info | grep -i "root dir"`; скорее всего, каталог перенесён в `/opt`.

**Что закрыто в коде.** Потолок на логи контейнеров (10 МБ × 3 файла для
app, 5 × 2 для бота) и уборка `/data/files`: готовые макеты живут неделю,
загруженные картинки два месяца. Разный срок не случаен — на загруженные
ссылаются сохранённые проекты. На том переполнении ни то ни другое не было
причиной, но 14 МБ логов за четыре дня работы — это гигабайт в год, так что
потолок нужен.

Настройка логов сделана на уровне сервиса, а не демона: править
`/etc/docker/daemon.json` значило бы перезапускать Docker и вместе с ним
соседнюю гачу.

**Что нужно сделать руками один раз** — ограничить журнал systemd, иначе
он снова дорастёт до гигабайтов:

```bash
sudo mkdir -p /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=200M\nSystemMaxFileSize=20M\n' \
  | sudo tee /etc/systemd/journald.conf.d/size.conf
sudo systemctl restart systemd-journald
journalctl --disk-usage
```

**Куда смотреть, если место кончилось снова.** Сначала измерить, а не
чистить наугад:

```bash
df -h /
du -xh --max-depth=1 / 2>/dev/null | sort -hr | head -12
du -xh --max-depth=2 /var/lib/docker 2>/dev/null | sort -hr | head -12
docker system df -v | head -30
du -sh /var/lib/docker/containers/*/*-json.log 2>/dev/null | sort -hr | head
journalctl --disk-usage
```

Свободное место видно и без SSH — `/api/health` теперь возвращает
`disk_free_mb`, `disk_used_pct` и число файлов.

**Про размер диска.** 20 ГБ на две системы, одна из которых носит внутри
Chromium, — тесно. Образ `dznow-app` с Playwright весит около 2 ГБ, и каждая
пересборка какое-то время держит на диске и старую версию. Чистить
`docker image prune -a -f` после каждой выкатки — обязательная привычка,
пока диск не станет больше.

## Чего не хватает для настоящего продакшена

Это честный список, а не придирки — просто на тестах оно не мешает.

1. **SQLite и один рендер за раз.** Сейчас макеты собираются по очереди в одном
   потоке. Два человека нажали «Создать» одновременно — второй ждёт. Лечится
   очередью (Redis + RQ) и Postgres; оба пункта уже стоят в плане в README.
2. **Файлы копятся вечно.** `/data/files` никто не чистит. До первых сотен
   картинок это неважно, дальше нужна уборка по возрасту.
3. **Бренд агентства — константа** в `api/app/main.py`. Под нескольких клиентов
   нужна таблица арендаторов, это тоже в плане.
4. **Шрифты тянутся из сети** при каждом рендере. Если у сервера пропадёт доступ
   к `fonts.googleapis.com`, Chromium молча подставит системный шрифт и макет
   уедет. Лечится складыванием шрифтов в образ — `tools/fetch-fonts.ps1`
   и раздел «Шрифты» в README.
5. **Нет бэкапа.** Том `dznow-data` стоит забирать `docker run --rm -v
   dznow-data:/d -v $PWD:/out alpine tar czf /out/dznow-data.tgz -C /d .`
